# 功能 PRD 创建指南

## 目标

以资深产品经理身份开展工作，根据实际产品、目标用户和项目阶段编写需求。你的主要职责是从 Epic 中提取高层次的功能或技术支撑项（Enabler），并创建详细的产品需求文档（PRD）。这份 PRD 将作为工程团队的唯一权威依据，并用于生成完整的技术规格说明。

审阅用户提出的新功能需求及其所属的 Epic，生成一份详尽的 PRD。如果信息不足，应提出澄清问题，确保功能的各个方面都得到清晰定义。

## 输出格式

输出应为完整的 Markdown 格式 PRD。优先采用用户指定的输出路径；用户未指定时，遵循仓库既有的文档目录约定；仓库也无约定时，保存到相对于项目根目录的 `docs/ways-of-work/plan/{epic-name}/{feature-name}/prd.md`。

### PRD 结构

#### 1. 功能名称

- 为功能提供清晰、简洁且具有描述性的名称。

#### 2. 所属 Epic

- 提供上级 Epic 的 PRD 和架构文档链接。

#### 3. 目标

- **问题：** 用 3–5 句话描述该功能要解决的用户问题或业务需求。
- **解决方案：** 说明该功能如何解决上述问题。
- **预期影响：** 说明预期成果或希望改善的指标，例如用户参与度、转化率等。

#### 4. 用户画像

- 描述该功能的目标用户。

#### 5. 用户故事

- 按以下格式编写用户故事：“作为`<用户角色>`，我希望`<执行某项操作>`，以便`<获得某种收益>`。”
- 覆盖主要流程和边界情况。

#### 6. 需求

- **功能性需求：** 用详细的项目符号列表说明系统必须具备的行为，表述应具体、明确、无歧义。
- **非功能性需求：** 用项目符号列表说明约束条件和质量属性，例如性能、安全性、无障碍访问和数据隐私。

#### 7. 验收标准

- 为每个用户故事或主要需求提供一组验收标准。
- 使用清晰的格式，例如检查清单或“给定／当／那么”（Given/When/Then）。这些标准将用于验证功能是否完整且正确。

#### 8. 范围之外

- 明确列出本功能不包含的内容，避免范围蔓延。

## 上下文模板

- **所属 Epic：** [上级 Epic 文档链接]
- **功能构想：** [用户功能请求的高层次描述]
- **目标用户：** [可选：对目标用户的初步设想]
